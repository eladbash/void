Void

A complete visual and interaction redesign of Void — the desktop tool that finds and reclaims developer build artifacts. Every screen, both themes, specified down to the token. Nothing here has been built into the app yet; this document exists to be argued with.

01

Direction

the argument

Void deletes things. That single fact should decide every design choice in it, and in the current UI it decides none of them. The redesign is organised around three moves, each of which fixes something that is presently wrong rather than merely plain.

One — the statistics dissolve into the list

Today a 320 px panel holds a nine-segment donut, a bar chart, and a stack of cards that print the same numbers three times, and it auto-opens the moment a scan completes — shoving aside the results the user just waited for. The panel is deleted. Group headers become the bar chart, typographic weight becomes the size hierarchy, and a disk meter answers the question the donut never did: how much of my disk is this? Every statistic survives; none of them cost the list any width.

Two — risk belongs to the action, not the item

This is a correctness fix disguised as a design change. CleanableItem.risk and CleanAction.risk are different fields, and they disagree: SimulatorDevices is a Caution item holding a Danger action, and ~/Downloads is a Safe item holding rm -rf. The current UI shows the item's risk and then silently runs available_actions[0]. The redesign shows the risk of the action that will actually run, and makes that action visible and changeable on every row.

Three — confirmation friction scales with real risk

A dialog that looks the same whether you are deleting node_modules or emptying your Maven repository trains people to click through it. An all-safe batch gets a 280 px modal and one click. A batch containing Caution actions gets each one itemised with its literal command. A batch containing a Danger action requires typing delete. The friction is the signal.

A constraint worth stating. Everything drawn here is buildable against the existing Rust backend except nine items, listed in §08. Four of them — persisting AppConfig, a batch-complete event, a cancellation token, and a disk-usage command — are small. The History screen and honest permission-denied reporting are not. Screens that depend on missing backend work are marked needs backend so nothing here reads as shippable when it isn't.

Screens

11 states · both themes

Every screen at its true size — 900×700, the app's default window. Each is shown in dark first, then light directly beneath it, rendered from the same markup so the two can't drift apart. The notes beside each screen explain the decisions that aren't self-evident.

5a

First run

900 × 700 · content max 440

The most common first-run failure isn't confusion about the button — it's scanning the wrong root, or on macOS being unable to read it. So the scan root is stated before the first scan, with a one-click route to change it. That turns a baffling empty result into a fix, and quietly teaches that roots are configurable at all.

5b

Scanning

streaming · no separate screen

There is no dedicated scanning screen. Results stream into the real table as ItemFound arrives — a separate progress screen would throw away the only user-visible benefit of the streaming architecture. What's added is a per-scanner ticker, which is the honest answer to "is it stuck?" when eleven scanners run concurrently and one of them is slow.

Dark
Light
Notes
  • 1Progress is indeterminate and stays that way. Total path count is unknowable up front; a fake determinate bar would be a lie.
  • 2The ticker shows three states per ecosystem — pending, running, ✓ n done. Driven straight off ScannerStarted / ScannerCompleted.
  • 3Group order freezes during the scan. Groups appear in arrival order and re-sort once, at ScanComplete. Re-sorting per event produces an unreadable jumping list.
  • 4Selection is disabled mid-scan — a later event can supersede an item you've already ticked.
  • 5The headline counts up live. This is the best moment in the product; it gets the animation budget.
5c

Results — the core screen

900 × 700 · 52+64+40+28+492+24

5d

Pre-clean confirmation

modal 560 wide · max 600 tall

Leads with method, not risk — what physically happens is what determines recoverability, and rm -rf is a fact where a risk label is a scanner's opinion. Safe items are counted, never listed; only Caution and Danger get individual rows. With no Caution or Danger in the batch the whole attention section disappears and the modal is ~280px tall.

Dark
Light
Notes
  • 1The literal command is shown for every Command and DockerPrune action. SafetyChecker never inspects command arguments — this string is the only real disclosure the user gets.
  • 2Type-to-confirm appears only when a Danger action is in the batch. The word is delete, lowercase, unlocalized.
  • 3“Prefer Trash where available” is checked by default and lives next to the commit button, because it is the one control that can turn a Danger batch into a Safe one. Toggling it re-computes the modal live.

5e

Cleaning

in place · determinate

The modal closes and the user returns to the table, because that's where the objects being acted on live. execute_batch is a strictly sequential loop, so this is a queue, not parallel bars — one active, the rest waiting — and the progress is genuinely determinate. Failures don't stop the batch, so failed rows stay put while successful ones collapse away; by the end the table has filtered itself down to exactly what didn't work.

Dark
Light
Notes
  • 1No Stop button. There is no cancellation token in execute_batch. A Stop button that doesn't stop is worse than none — this needs backend work first.
  • 2The failed row keeps its place, tinted, with the raw error in monospace and a Retry. Machine text is always monospace, always selectable, never folded into a sentence.
  • 3cargo: not found in PATH is the most likely real failure, so it gets a contextual fix chip that swaps to the item's RemoveDir action and re-queues it.
  • 4“freed so far” uses bytes_freed where it's non-zero and estimated_savings_bytes otherwise — Command and DockerPrune always report zero.

5g

Item detail drawer

400 wide · overlay <1280, inline ≥1280

The screen the current app has no equivalent of. Opening it does not change selection — inspecting and choosing are separate acts. Its centre is the action radio list, where every option shows its label, its verbatim description, the literal command or method, what it frees, and whether it is recoverable. Only two actions in the entire product are recoverable, and the drawer says which.

Dark
Light
Notes
  • 1Changing the selected action immediately updates the row's risk edge and badge, because risk is a property of the action.
  • 2Frees unknown — never 0 B. Every npm/yarn/pnpm project-cache action, every Docker action, and every per-project DerivedData action reports estimated_savings_bytes: 0.

5k

Error & permission states

banner 44 · issues sheet 480

Today ScanEvent::Error goes to console.error and vanishes. A scan can emit dozens, so they get a status-bar chip and a sheet — never a modal, never a toast each. The permission banner is the important one: because unreadable directories are dropped rather than reported, the failure mode is invisible absence, and absence with no explanation reads as “this tool doesn't work.”

Dark
Light
Notes
  • 1Identical messages group with a ×N multiplier rather than repeating.
  • 2“Nothing to clean” routes to Check scan roots first, not to a retry — it's almost always a wrong-root or permissions problem.
  • 3A filter matching nothing is an inline 120px state, not a full-page one. A 56px empty state punched into a filtered list is a jarring hole.

02

Color

141 pairings · 0 failures

The app icon is a pure-black field with a luminous azure V. The current CSS contradicts its own icon — every neutral sits at hue 270–277 (violet-navy) while the icon glows at hue 253, and the background is a murky dark rather than a void. The new palette is derived from that glow: neutral hue 254, accent hue 252, on a ground of #010306.

What was measured wrong

These aren't taste judgements. Each row is a computed number against the current palette.

The root cause is structural, not aesthetic. Eleven categorical hues and three signal hues were placed on the same wheel, at the same chroma, with no lightness strategy. Collisions were inevitable. The fix is a rule, not a repaint: signal colors and data colors are two registers that never mix — different chroma bands, different geometry, and reserved hue arcs around each risk color.

Risk — the one distinction that must never fail

Safe is jade (hue 170), not green. That frees pure green for Node.js, and more importantly a jade keeps blue-channel energy — which is exactly what survives red-green dichromacy. Moving Safe from hue 150 to 170 lifted worst-case colorblind separation from 13.0 to 16.9.

Color is never allowed to carry the signal alone. Safe↔Danger improves from ΔE 8.2 to 19.8, but the light theme's worst case is still 10.8 — dark chromatic text compresses toward brown under dichromacy. So every risk mark carries three channels: a glyph (✓ check / triangle / octagon), a shape (Safe is a full pill; Caution and Danger are squarer, and Danger adds a 2px left rule), and the word itself. Never a bare colored dot.

Ecosystems — eleven categories that don't fight

Brand hues were used as seeds, then positions were solved to maximise worst-case pairwise separation while honouring reserved arcs around the three risk hues. Lightness is a deliberate alternating ladder, not a constant — eleven equal-lightness categoricals caps worst-case separation at ΔE 3.2, because hue alone cannot carry eleven levels.

03

Typography

23 roles · 2 faces

Two faces, not three. Inter variable with the optical-size axis (14–32) gives display-optical treatment without a third download, so no separate display face is warranted; Geist Mono carries paths, commands, sizes and counts. The base size is 13px and the scale is quantised to whole pixels below 20px — a modular ratio produces sub-pixel sizes in the 10–18px band where 95% of this UI lives, and those render soft. Hierarchy comes from weight and line-height instead: three distinct roles at 13px, three at 11px.

Scale

Numbers are the content

This is a tool for auditing quantities, so numerals get more care than the prose does.

RuleWhy
tabular-nums at 10 mandatory sitesSize column, staleness, metrics, bar values, the Clean button total, progress %, scan duration, filter counts, status counts. Proportional digits make a column of sizes unscannable.
Size is two elements, never one string<span class="size-num">1.4</span><span class="size-unit">GB</span> with a 3px flex gap and a 16px unit gutter. A space character isn't tabular and breaks decimal alignment.
Four typographic size tiers≥10 GB at 15px/620, 1–10 GB at 14px/620, 100 MB–1 GB at 13px/560, <100 MB dimmed. Gigabyte rows visually rise out of the list — the cheapest possible size hierarchy.
Base 1000, units B / kB / MB / GBMatches Finder's Get Info, which is the number users compare against. Lowercase k is the correct SI prefix; KB on a base-1000 scale is wrong and developers notice.
Keep the trailing .0 below 102.0 GB, not 2 GB. In a column a consistent decimal position beats brevity.
Exact counts, never 1.2kAbbreviating in a tool where the number is the audit is a lie for no gain. The one exception is the tray tooltip, which the OS truncates hard.
Two time registersRows get 94d — a sortable magnitude in a 56px column. Tooltips get 3 months ago · Feb 14, 2026, because that's when the user is deciding whether to delete. Never “recently”.
Every nullable number has an em-dash stateThree exist: days_stale, last_modified, project_name. An empty cell reads as a rendering bug; — reads as “not applicable”.
Two byte formatters currently disagree. Rust fills size_display via ByteSize (base 1024) and the row renders that; the donut, cards, bars and Clean button use the JS formatBytes() (base 1000). A 1.5 GiB item shows 1.5 GB in its row and contributes 1.6 GB to the total. Pick one — the JS one, from size_bytes — and ignore size_display entirely.

Paths

A path is the item's identity — three node_modules/ rows are indistinguishable without it — so it lives permanently on line 2 rather than behind a hover tooltip. Because it's monospace, truncation is arithmetic, not measurement: measure the character advance once, compute a budget, then grow segments outward from the leaf. Four emphasis roles inside one string, with the separators as the dimmest element so the names read as names.

Wordmark

The mark is a ring with a gap at 45° — an event horizon — and it is also the scan indicator and the tray glyph. One shape doing three jobs is what makes a small app feel designed rather than decorated. Sentence case, because caps would make it a product category and sentence case makes it a name.

Delete the header subtitle. “Developer disk space reclaimer” sits under the wordmark on every launch, explaining the app to someone who already opened it. That slot is worth live state: 384 items · scanned 2m ago, or Scanning ~/Developer · 1,204 dirs.

Layout & shell

rail + command bar

Void has three destinations and one dominant surface. A top nav would spend 52px of vertical space — the scarcest resource in a 700px-tall window — on three links. A left rail spends 56px of horizontal space, which is 6% at 900px and 4% at 1440px. Vertical space buys list rows; horizontal space is comparatively abundant. The rail wins.

The window also needs minWidth: 720, minHeight: 560 — it currently has no minimum, and the design does not survive below that.

Vertical budget at 900 × 700

When the list scrolls past 24px the summary strip condenses from 64 to 36 and reflows to one line — returning 28px, over half a row, on a screen where every row counts.

Motion & depth

mostly restraint

This is a tool people open many times a day, so the interesting part of the motion spec is the list of things that must not animate. The streaming scan is the hard case: rows arrive faster than they can be read, and every instinct to make that feel alive makes it harder to use.

Streaming rows — the crux

RuleReason
Coalesce arrivals into one requestAnimationFrame batch and append a DocumentFragmentThe current code rebuilds the whole list's innerHTML on every item_found — O(n²) across a scan.

Depth

Shadows are for things that float; borders are for things that sit. Almost everything in this design sits: rows, cards, panels, the toolbar, the summary strip and every control are elevation zero, separated by a 1px border. Only menus, popovers, tooltips and modals float.

In dark theme a drop shadow on a near-black ground conveys nothing, so elevation is carried by three things instead: a step up the surface ramp, a 1px outer ring, and an inset 0 1px 0 rgb(255 255 255 / .055) lit top edge. That top edge is what actually reads as “raised”.

Where to start

If only one thing ships from this document, it should be risk-follows-the-action plus the per-row action picker. It's the only change here that prevents a user from deleting something they didn't intend to. The palette swap is second — it's mechanical, it's a single CSS block, and it fixes an AA failure and a colorblind-safety failure at the same time. The layout work is third; it's the largest change and the least urgent, because the current layout is merely cramped rather than wrong.
